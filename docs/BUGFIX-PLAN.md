# 词航全链路 Bug 修复计划（2026-10-27）

## 原则

- 不再用"跑通主流程"代替真实组合场景验证
- 每个修复必须带回归用例：状态合并、重测、跨账号、跨设备、日志裁剪、音频失败、例句缺档
- 先修数据正确性，再修学习算法，再修内容质量与体验

## P0：数据与复习正确性

### 1. v2.0 新同步字段没有正确合并

**现象**：网页和 App 的 `bandStats`、`knowledge` 可能不同，导致预计认识词数和发词位置不同。

**根因**：`merge_learning_states` 对这些字段直接采用新写入值，旧客户端或另一台设备缺少字段时会覆盖/清空已有值。该问题在 v2.0 引入后出现。

**修复**：
- `bandStats` 按档位合并证据，不能因为一端缺字段就清空
- `knowledge` 按单词合并证据，保留最近学习记录更多的一侧
- `placementResetAt` 期间以新定级数据为准，其他情况按证据量/最近活动合并
- 增加"v2.0 字段存在/缺失混合同步"回归用例

### 2. FSRS 的 last_review 依赖日志，日志裁剪后间隔会退化

**现象**：历史卡片可能再次短期重复，长期稳定度增长不可靠。

**根因**：`lastReviewDate` 从 `S.log` 推导，而客户端只保留最近 1200 条；曝光日志增多后，老的 learn/review 记录更容易被挤掉，导致 FSRS 将经过天数算成 0。

**修复**：
- 在卡片 FSRS 状态中显式保存 `last_review`，以它为主、日志推导为兜底
- 服务端 `/fsrs/review` 返回 `last_review`，双端保存并回传
- 增加"日志裁剪后仍能正确计算间隔"回归

### 3. 合并后的日志没有上限，状态会越来越大

**现象**：服务端 `user_state` 中 log 已超过客户端裁剪上限（uid6 当前 2831 条），跨设备后状态继续膨胀。

**根因**：服务端合并日志时只做事件计数合并，不执行客户端的 1200 条裁剪。

**修复**：
- 合并后按日期和事件类型保留最近 1200 条，优先保留 learn/review/probe/placement，曝光日志单独限流
- 增加多轮合并后大小不超限回归

### 4. 时间戳策略仍可能让旧本地状态覆盖新服务器状态

**现象**：不同端显示不同卡片数、发词位置、连续天数。

**根因**：`localTs > remote.updated_at + 2` 就优先本地，但 `save()` 会在很多日常操作中刷新本地时间，时间新不代表内容更新。简单按时间戳判断容易让旧内容覆盖新内容。

**修复**：
- 拉取时执行字段级合并，而不是二选一：日志并集、卡片按最近活动、后验按证据量、设置按用户最后明确修改
- 只有明确存在未同步本地修改时，才在拉取后立即补推，且推送必须带账号 owner 和状态快照
- 增加"A 端学习后 B 端再打开"和"B 端旧状态后写入"回归

## P1：学习逻辑与内容正确性

### 5. 已掌握词仍显示旧个性化例句

**现象**：用户已经确认掌握的词，仍可能出现早期个性化例句，违反"掌握后不再出现"。

**根因**：展示层只检查 `S.personalized[word]` 是否存在，没有过滤 `isMastered`；`autoPersonalize` 在"今天没有薄弱词"时也不清理旧映射。

**修复**：
- 展示个性化例句前过滤已掌握词
- 每日结算时清理已掌握词的个性化映射
- 双端增加"毕业后不再显示个性化例句"回归

### 6. 三句套装没有真正使用例句库

**现象**：设计要求是"1 条例句库句 + 2 条生成句"，但 `sentence_trio` 查询只允许 `llm-%`，Tatoeba 永远不会进入三句套装。

**根因**：`sentence_trio` 的缓存查询遗漏 `genMethod='tatoeba'`。

**修复**：
- 缓存查询同时允许 Tatoeba，并优先用自然语料作为基础句
- 缺档时仍按质量门生成，保证三档完整
- 增加"有语料词的三句组成"和"无语料词的生成补缺"测试

### 7. 定级先验仍可能虚高或抖动

**现象**：用户反复感觉高估/低估。当前先验不足时默认每档 0.5，可能使 `ΣP(认识)` 虚高；分层边界仍受少量题影响。

**修复**：
- 未学词先验不要固定 0.5，改为基于定级证据的弱先验并显示不确定性
- 预计认识词数同时展示区间/级别，不把它当精确真值
- 用真实定级日志评估偏差，不再只调全局权重

### 8. 独立校验失败时可能显示误导性结果

**现象**：题目拉取失败也会被计入完成逻辑，可能得到没有意义的独立估值。

**根因**：`answerValidation(countEvidence=false)` 只是跳过题目，最后仍按通过/失败混合计算并展示结果。

**修复**：
- 有效题目不足时明确提示"校验不可用，请重试"，不展示伪精确估值
- 保留独立校验不影响学习状态的回归

## P2：质量与维护

### 9. 评审模型失败时默认放行低质例句

**根因**：`quality_check` 异常时返回 4，等于把未知质量当成合格。

**修复**：评审不可用时优先使用已审过的静态句，或延后重试；不要默认放行。

### 10. 历史污染状态需要修复工具和说明

**现象**：`zorro` 和 `zorrozou` 曾出现相同的 frontier/track 字段，说明早期跨账号竞态已造成污染。

**修复**：
- 提供只读诊断：比较两个账号相同字段的来源，不直接自动改用户数据
- 需要修正时先备份，再让用户重新定级/确认
- 保留防再次污染回归

## 执行顺序

1. **P0-1 新字段合并 + P0-2 last_review 卡片化 + P0-3 日志上限 + P0-4 拉取合并**
2. **P1-5 掌握后隐藏个性化 + P1-6 三句套装接入例句库**
3. **P1-7 先验与不确定性 + P1-8 校验失败提示**
4. **P2 评审失败兜底、历史污染诊断工具**
